# 설계 철학

CCForge의 규칙은 아래 생각에서 나왔다. 규칙을 고치거나 더할 때는 먼저 이 생각에 맞는지 본다.

## 1. 무엇을 만들지는 사용자가 정하고, 어떻게 진행할지는 묻지 않는다

사용자가 결정하는 것은 **무엇을 어떻게 만들지**다. 그 밖의 진행은 팀이 알아서 한다.

- **구현 계획은 승인받는다.** 분석원이 요구를 분석하면 팀장이 구현 방식, 영향 범위, 단계, 구현하면서 생길 문제점을 요약해 보고하고, 사용자가 승인해야 실행 팀원에게 넘긴다. 무인 실행이면 `plan.require_approval: false`로 보고만 하고 진행한다.
- **요구사항이 잘못됐거나 구현할 수 없으면 사용자에게 돌아간다.** 실행 중에 드러나도 마찬가지다. 분석원이 무엇이 문제인지와 대안을 정리하고, 팀장이 사용자에게 구체화할지 다른 방식으로 갈지 묻는다. 팀이 요구를 임의로 바꾸지 않는다.
- **진행 방식은 묻지 않는다.** step 배정, 병렬 여부, 검토 관점, 재작업은 팀이 정하고 한 줄로 알린다. 설문은 무엇을 만들지가 갈릴 때만 한다. 규모가 크다는 것은 물을 이유가 아니다.
- **헷갈리면 추측하지 않고 묻는다.** 실행 팀원은 분석원에게, 분석원은 (사용자가 정할 일이면) 팀장을 거쳐 사용자에게 묻는다.
- 설정이 깨졌거나 규칙 파일을 읽을 수 없어도 **멈추지 않는다.** 기본 동작으로 진행하고 알린다.

## 2. 중간에 끊겨도 잃는 것이 없어야 한다

사용자가 끊을 수도 있고 세션 한도에 걸릴 수도 있다. 어느 지점에서 끊겨도 `resume`으로 이어갈 수 있어야 한다.

- 상태는 기억이 아니라 **파일**에 있다. 팀원은 Result를 파일로 남기고 step의 `log.jsonl`에 한 줄씩 적는다. 팀원은 재시작하면 사라지므로 Lead는 파일과 git만으로 상태를 맞추고 팀원을 새로 만든다.
- 복구할 때는 **기록보다 저장소의 실제 상태를 믿는다.** 커밋은 됐는데 기록 전에 끊긴 경우를 git에서 직접 확인한다.
- 같은 메시지를 다시 받아도 결과가 같아야 한다(멱등성). 이미 있는 Result는 다시 만들지 않는다.

## 3. 에이전트는 세 유형이고, 달라지는 것은 스킬로 뺀다

에이전트는 **분석형, 실행형, 검증형** 세 유형뿐이다. 나중에 만드는 에이전트도 이 셋 중 하나다.

- **유형이 프로토콜을 정한다.** Result 봉투는 하나이고, `status`·`blocked.type`은 유형마다 고정이다. 분석형은 `READY`/`BLOCKED`, 실행형은 `DONE`/`BLOCKED`, 검증형은 `PASS`/`FAIL`/`BLOCKED`를 낸다. 에이전트마다 달라도 되는 것은 `payload`뿐이며, 그것도 유형 공통 필드는 담아야 한다.
- **Lead는 에이전트를 이름으로 알지 않는다.** epic을 시작할 때 `agents/*.md`의 머리(`name`, `type`, `description`)를 읽어 목록을 만들고, 유형과 `description`의 대상으로 팀원을 만든다. 절차 문서에는 유형만 적혀 있어 에이전트를 더해도 절차가 바뀌지 않는다. 에이전트 등록은 정의 파일 하나를 두는 것으로 끝난다.
- **유형마다 기본 에이전트가 하나 있다.** 대상을 한정하지 않은 에이전트이고 기본 제공은 `analysis`, `coder`, `reviewer`다. 대상을 좁게 적은 에이전트(예: "의존성 파일의 취약점을 외부 도구로 검사한다")는 그 대상의 Task에서 기본 에이전트 대신 뽑히고, 검증형은 기본 검증과 함께 호출된다.
- **규칙 목록만 다른 일은 에이전트가 아니라 스킬이다.** 산출물 종류(코드, 문서, 명세)와 검증 관점처럼 **일의 성격에 따라 달라지는 규칙은 워크플로 스킬**이다. 다른 도구·모델·절차가 필요할 때만 에이전트를 만든다. 언어와 도구에 관한 것은 스킬이 아니라 프로젝트의 `CLAUDE.md`에 둔다(8번).
- **주제 지식은 워크플로 스킬 한 곳에 두고, 관점은 에이전트 정의에 직접 적는다.** 코드 구조나 문서 작성 같은 주제의 규칙은 누가 읽어도 같은 내용이므로 `skills/<이름>/`에 한 번만 적고 모든 에이전트가 같은 파일을 읽는다. 에이전트마다 다른 것은 그 지식으로 무엇을 하느냐다. 분석형은 계획에 반영하고, 실행형은 지켜서 만들고, 검증형은 위반을 찾는다. 이 방식은 주제와 무관하게 일정하므로 스킬로 빼지 않고 에이전트 정의 파일(`agents/<이름>.md`)에 직접 적는다.
- **같은 규칙을 여러 파일에 적지 않는다.** 규칙이 한 곳에만 있으면 만든 쪽이 따른 규칙과 검증하는 쪽이 확인하는 규칙이 같은 문장이다. 에이전트를 새로 만들거나 이미 있는 에이전트를 가져올 때는 `agent-builder`가 CCForge의 규약(유형, 봉투, 워크플로 스킬을 쓰는 방식)에 맞춰 편입한다.
- **검토는 여러 검토 팀원이 독립으로 한다.** 기본 검증 하나는 항상 있고, 관점 스킬마다, 대상이 맞는 검증형 에이전트마다 검토 팀원이 붙는다. 같은 round에서 전원이 `PASS`여야 실행 팀원이 팀장에게 완료를 보고한다.
- **팀원끼리 직접 대화한다.** 재작업 루프와 설계 질문은 팀원 사이에서 끝난다. 팀장에게는 계획, step 완료, 팀 안에서 풀 수 없는 일만 온다. 그래서 팀장의 컨텍스트는 사용자와 브랜치 관리에만 쓰인다.
- **팀은 동시에 돌 일이 있을 때만 만든다.** agent teams는 팀원마다 컨텍스트를 따로 쓰므로 토큰이 팀원 수만큼 든다. 동시에 돌 step이 없거나 작은 일이면 같은 정의를 서브에이전트로 차례로 호출한다(순차 방식). 팀은 총원 `team.max_members`(기본 5) 안에서 분석원 1, 검토 팀원 1, 나머지 실행 팀원으로 꾸리고, epic이 끝날 때까지 유지해 같은 코드를 다시 읽지 않게 한다. 관점 스킬(보안 등)은 검토 팀원을 따로 두지 않고 기본 검토 팀원이 함께 본다.
- **지켜야 하는 조건은 문장이 아니라 코드로 지킨다.** "검토 전원 PASS일 때만 완료"와 "할 일이 남았는데 멈춘 팀원"은 `TaskCompleted`·`TeammateIdle` hook(`hooks/ccforge_check.py`)이 `log.jsonl`을 보고 판단한다. 메시지 형식이 틀려도 흐름이 깨지지 않는다.

## 4. 브랜치는 사용자가 정한다

기본은 epic 하나가 브랜치 하나다. **사용자가 나눠 달라고 할 때만** 브랜치(job)를 나누고, 나누는 기준을 말하지 않았으면 분석원이 제안해 사용자가 확인한다. 브랜치가 끝날 때마다 원격에 푸시한다(강제 푸시와 PR 생성은 하지 않는다).

- 브랜치 이름이 먼저 정해지고 job 디렉터리 이름은 그것을 따른다(`/`만 `_`로). 브랜치와 작업 기록을 이름으로 바로 짝지을 수 있어야 한다.
- 브랜치가 여럿이면 `order` 순으로 하나씩 진행한다.
- **메인 작업 트리는 건드리지 않는다.** 체크아웃·커밋·병합은 `.ccforge/worktrees/<epic_id>/` 아래 통합 worktree와 실행 팀원별 worktree에서 한다. 사용자는 그동안 메인 트리에서 다른 일을 해도 된다. 실행 팀원의 worktree는 epic 동안 재사용해 의존성 설치를 한 번만 한다.
- **step마다 step 브랜치에서 작업하고, 독립인 step은 동시에 진행한다.** 동시에 도는 step은 서로 다른 파일을 맡는다(공식 권장대로 팀원마다 파일 소유를 나눈다). 전원 `PASS`하면 Lead가 job 브랜치에 fast-forward로 병합해 실행 팀원의 커밋을 그대로 남긴다. 먼저 병합된 step과 충돌하면 그 step의 실행 팀원이 rebase로 충돌을 풀고 다시 검증받는다.
- **커밋은 실무처럼 한다.** 실행 팀원이 논리 단위로, 팀의 커밋 규약(없으면 Conventional Commits)대로 커밋한다. 재작업은 fixup 커밋으로 남기고 검토를 통과하면 합친다. 검토 팀원은 커밋 메시지와 단위도 본다. 팀장은 커밋을 새로 만들지 않는다. 여러 worktree에서 동시에 빌드·테스트를 돌려도 되는지(포트·공용 캐시)는 분석원이 판단하고, 아니면 순차 방식으로 하나씩 진행한다.

## 5. 팀의 규칙은 팀의 파일에 둔다

CCForge가 팀의 방식을 정하지 않는다.

- 팀 규칙은 `rules/`에 파일로 둔다. 모든 작업에 적용할 것은 `rules/common/`, 특정 영역에만 적용할 것은 `rules/<주제>/`에 두고, 적용한 규칙은 검토 팀원이 하나씩 검증한다. **있으면 따르고 없으면 기본 동작**이다. 브랜치 규약만은 예외로, 없으면 첫 브랜치를 만들기 전에 설문으로 한 번 묻고 답을 `.ccforge/branch-convention.md`로 저장한다(`.claude/` 아래는 Claude Code가 쓰기를 막는다). 브랜치 이름은 PR과 기록에 그대로 남아 나중에 바꾸기 어렵기 때문이다. 일을 맡기기 전인 시작 시점에만 묻고, 진행 중에는 묻지 않는다.
- git 무시 규칙도 프로젝트의 것이다. `.ccforge/`는 프로젝트의 `.gitignore`에 넣고, CCForge는 무시 파일을 만들거나 고치지 않는다.
- 설정 파일에는 **정말 값으로 조절할 것만** 둔다(동시 진행 step 수, 재시도 횟수, job 사이 멈춤). 규약으로 정할 수 있는 것은 설정 키로 만들지 않는다. 설정이 늘수록 CCForge를 이해하기 어려워진다.
- 설정에 있는 값은 문서가 숫자를 직접 적지 않고 **설정 키를 가리킨다.** 기본값은 한 곳에만 적는다.

## 6. 문서가 곧 동작이다

CCForge는 코드가 아니라 문서로 되어 있고, 에이전트는 문서에 적힌 대로 움직인다. 문서끼리 어긋나면 그것이 곧 버그다.

- **읽는 사람마다 문서가 하나다.** Lead는 `commands/lead.md`, 팀원은 자기 `agents/<name>.md`만 읽고 일할 수 있어야 한다. 다른 문서를 따라가게 만들지 않는다.
- 용어를 바꿀 때는 **기계적으로 치환하지 않고 문맥을 읽고 고친다.** 단어만 바꾸면 뜻이 틀린 문장이 남는다.
- 고친 뒤에는 전체 일관성을 다시 본다. 구조를 바꿀 때 생기는 어긋남은 자동 검사보다 읽어서 찾는 경우가 많다.

## 7. 컨텍스트는 비용이다

Lead는 epic이 끝날 때까지 한 세션에서 돌고, 읽은 것은 전부 이후 모든 턴의 비용이 된다.

- Lead는 **소스 코드를 읽지 않는다.** 이해하는 일은 분석형과 실행형에 맡긴다.
- 문서는 통째로 읽지 않는다. 복구 절차(`lead-resume`)와 브랜치 규칙(`lead-branching`)은 필요할 때만 읽는 스킬로 떼어 두었다. 스킬과 에이전트 정의는 머리만 읽는다. Result는 라우팅에 필요한 필드(`status`)만 뽑아 본다.
- 작은 일은 분석도 보고도 짧게 한다. 길이가 계속 느는 값에는 상한을 둔다. 긴 작업은 job 사이에서 끊고 새 세션으로 이어가는 편이 싸다.

## 8. 여러 환경에서 쓸 수 있어야 한다

CCForge는 한 저장소의 설정이 아니라 프레임워크다.

- **CCForge는 쓰는 프로젝트의 `.claude/` 안에 둔다.** 전역으로 설치하지 않는다. 그래서 워크플로는 그 프로젝트에서만 켜지고, 프로젝트마다 에이전트와 스킬을 자기 사정에 맞게 고칠 수 있으며, 저장소에 커밋하면 팀원도 같은 것을 쓴다. 그 안에서도 CCForge의 파일(`agents/`, `commands/`, `protocols/`, `skills/`)과 프로젝트의 파일(설정, 팀 규칙, 작업 기록)은 자리가 나뉘어 있어, CCForge를 다시 복사해도 프로젝트의 것은 바뀌지 않는다.
- **언어와 도구에 관한 내용은 프로젝트의 `CLAUDE.md`에 넣는다.** 쓰는 언어와 프레임워크, 테스트·빌드·린트 명령, 패키지 관리자가 여기에 해당한다. CCForge의 문서와 스킬에는 넣지 않는다. **코딩 관례(네이밍, 스타일, 팀이 쓰는 패턴)는 `CLAUDE.md`가 아니라 `rules/`에 적는다.** 언어에 묶인 내용이어도 팀이 정한 약속이기 때문이다. 그래야 같은 CCForge를 어떤 스택의 저장소에도 그대로 설치할 수 있고, 스택이 바뀌어도 고칠 곳이 `CLAUDE.md` 하나다.
- 자리는 셋으로 나뉜다. 무엇을 쓰고 어떻게 돌리는지(언어·도구·명령)는 `CLAUDE.md`, 팀의 약속(브랜치·git 규약, 코딩 관례 등)은 `rules/`, 일의 성격에 따른 규칙(코드 구조, 문서 작성, 검증 관점)은 스킬이다. 스킬은 어느 스택에서나 성립하는 말로만 쓴다.
- 환경마다 다른 것은 추측하지 않고 프로젝트가 적게 한다. `CLAUDE.md`에 테스트 명령이 없으면 에이전트는 저장소에서 찾아보되, 찾지 못하면 지어내지 않고 `BLOCKED`로 알린다.
