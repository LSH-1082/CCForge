# 코드 구조

워크플로 스킬이다(`protocols/skill-spec.md`). 누가 읽어도 같은 주제 지식만 적혀 있고, 이것을 어떻게 쓰는지는 읽는 에이전트의 정의 파일에 있다. 프로젝트에 명시된 것(`.claude/rules/`의 코딩 관례와 팀 규칙, `CLAUDE.md`, 린터 설정)이 아래 기본 규칙과 다르면 프로젝트의 것이 우선한다.

## 적용 대상

- 산출물: 소스 코드, 테스트
- 변경 파일: 프로그램 소스와 테스트 파일. 문서(`*.md`, `docs/`)만 바뀌는 step에는 적용하지 않는다.
- 검증 방식: 기본 검증

## 범위와 배치

- 요구사항은 화면이나 파일 단위가 아니라 도메인과 사용자 행동 단위로 해석한다.
- 영향 범위는 파일 목록뿐 아니라 영향을 받는 **모듈 경계**로도 표현한다.
- 코드가 들어갈 위치는 프로젝트에 정해진 구조 규약이 있으면 그 규약의 용어로 정한다. 규약이 없으면 프로젝트의 기존 관례를 따른다.
- 관례도 없으면 "지금 여러 곳에서 쓰이는가 / 독립적인 변경 이유가 있는가 / 책임이 좁은가" 셋을 기준으로 하고, 하나라도 불확실하면 **쓰는 곳 옆에 둔다**. 추측에 기댄 재사용을 위해 공용 위치로 올리지 않는다.
- 구조를 옮기는 작업은 어떤 파일이 어디로 가는지의 매핑을 먼저 정하고, 한 번에 전부 옮기지 않고 단계별로 끊어 각 단계가 독립적으로 빌드·테스트를 통과하게 한다.
- 파일을 옮길 때는 그 파일을 가져다 쓰는 곳의 경로, 테스트 파일, 모듈의 공개 진입점 파일을 함께 갱신한다.
- 이번 작업 범위 밖의 파일은 구조가 눈에 거슬려도 옮기지 않는다.

## 규칙

규칙마다 앞에 `[finding 유형·중요도]`가 붙어 있다. 의도한 예외라면 코드에 이유가 주석이나 ADR로 남아 있어야 하고, 근거가 남아 있으면 중요도를 `low`로 본다.

- [architecture·high] 의존성 방향을 지킨다. 상위 모듈이 하위 모듈을 쓰고, 그 반대나 순환 참조를 만들지 않는다.
- [architecture·high] 모듈의 공개 진입점으로만 가져다 쓴다. 남의 모듈 내부 파일을 직접 가져오지 않는다.
- [architecture·high] 공용 위치에는 비즈니스 로직을 두지 않는다. 특정 도메인 규칙은 그 도메인을 소유한 쪽에 둔다.
- [architecture·medium] 파일명은 기술 역할(`types.*`, `utils.*`, `helpers.*`)이 아니라 도메인 기준으로 짓는다.
- [architecture·medium] 프로젝트에 없던 새 계층이나 최상위 디렉터리를 임의로 만들지 않는다.
- [architecture·medium] 단일 사용 코드를 재사용 근거 없이 공용 위치로 추출하지 않는다.

## 판단이 갈리는 지점

규칙 위반이 아니라 판단이 갈리는 문제다. 누구도 임의로 결론내지 않고 선택지와 트레이드오프를 정리해 사용자에게 넘긴다.

- 모듈 경계를 어디서 끊을지
- 공용 추상을 만들지 말지
- 두 모듈을 합칠지 나눌지

## 확인 방법

- 변경된 각 파일이 속한 모듈을 먼저 확정하고, 그 파일이 다른 것을 가져다 쓰는 문장을 읽어 방향과 공개 진입점 경유 여부를 본다.
- 프로젝트에 구조 린터가 설정되어 있으면 보조로 쓸 수 있으나, 근거는 직접 읽은 코드로 삼는다.
- 이동 뒤에는 프로젝트의 `CLAUDE.md`에 적힌 린트·빌드·테스트 명령으로 확인한다.
- **이번 변경 범위 밖의 기존 구조**는 위반으로 보지 않는다. 이번 변경이 그 구조를 새로 늘렸을 때만 위반이다.
