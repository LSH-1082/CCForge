# 에이전트 만들기·편입하기

기준은 `protocols/task-result.md` 3.3.1(겹침 판정, 고치는 곳 ①–⑤)이고, 정의 파일의 형식은 기존 `agents/analysis.md`, `agents/coder.md`, `agents/reviewer.md`가 본보기다. 이 문서는 절차만 적는다. 두 곳이 다르면 `protocols/`를 따른다.

## 0. 경로

경로는 모두 프로젝트의 `.claude/` 기준이다(`agents/` = `.claude/agents/`, `protocols/` = `.claude/protocols/`, `commands/orchestrate.md` = `.claude/commands/orchestrate.md`). 프레임워크 저장소 자체에서 실행할 때는 저장소 루트 기준이다. 고친 파일은 그 프로젝트에만 적용된다. 다른 프로젝트에서도 쓰려면 프레임워크 저장소에 같은 변경을 반영해야 한다고 보고에 적는다.

## 1. 모드를 정한다

먼저 `agents/*.md` 전부와 `protocols/task-result.md` 3.3·3.3.1을 읽는다. 읽지 않고 쓰지 않는다.

| 요청 | 모드 |
|---|---|
| 새 역할이 필요하다 | **생성** (§2 겹침 판정을 통과해야 한다) |
| 이미 써 둔 에이전트 정의 파일(다른 프로젝트의 것, `.claude/agents/`의 것, 사용자가 붙여 넣은 것)을 이 워크플로에서 쓰고 싶다 | **편입** |
| 기존 에이전트의 동작을 바꾼다(워크플로 스킬을 쓰는 방식, 수행 절차, 원칙) | **확장** |
| 에이전트를 없앤다 | **삭제**. 기본 세 에이전트는 지우지 않는다 |
| `coder`가 만든 산출물을 받아 `reviewer`와 나란히 일할 에이전트(외부 도구 점검, 성능 측정 등) | **생성** 또는 **편입**. `coder` 뒤에는 여러 에이전트가 붙을 수 있다(§3.1) |
| 새 산출물 종류, 규칙 목록만 다른 새 검증 관점 | 에이전트가 아니다. `skill-builder`로 워크플로 스킬을 만든다 |
| 언어·프레임워크·도구가 다르다 | 에이전트도 스킬도 아니다. 프로젝트의 `CLAUDE.md`에 적는다 |

## 2. 겹침 판정 (생성·편입)

새 에이전트의 "유일한 질문"을 한 문장으로 적는다. 기존 질문은 "이 요구사항을 무엇으로 이해하고 어떻게 나눌 것인가"(`analysis`), "계획된 것을 산출물로 어떻게 만들 것인가"(`coder`), "만들어진 산출물이 기준에 맞는가"(`reviewer`)다. 새 질문이 이 중 하나에 들어가면 에이전트를 만들지 않는다. 편입 대상이 겹치면 그 파일의 고유한 규칙만 뽑아 워크플로 스킬(`skill-builder`)이나 기존 에이전트의 확장으로 옮기자고 제안한다.

요청에서 알 수 없는 것만 묻는다(`AskUserQuestion`이 있으면 그것으로, 한 번에): 유일한 질문, 언제 호출되는지(어느 `status` 뒤에), 돌아온 `status`마다 어디로 가는지, payload에 무엇을 담는지, 파일을 고치는지(`Edit` 필요 여부). 추정한 항목은 보고에 "추정"이라고 적는다.

## 3. 생성

결정한 내용을 표(유일한 질문, `request_type`, `status`, `blocked.type`, payload 키, 호출 시점과 행선지, tools·model, 받는 context)로 만들어 사용자 확인을 받은 뒤 아래 순서로 고친다. 하나라도 빠지면 Orchestrator가 그 에이전트를 부르지 못한다.

1. **`agents/<name>.md`** — 기존 정의 파일과 같은 절 구성으로 쓴다: `역할` → `핵심 원칙` → `프로토콜 (요약)` → `수행 절차` → `스킬`.
   - frontmatter: `name` = 파일명. `description`에 Task/Result 경로 문장. `tools`에 `Read`·`Write`·`Bash`(tmp→mv 때문), 산출물을 고치는 에이전트만 `Edit`.
   - `프로토콜 (요약)` 불릿 순서: `request_type` → `status` → `blocked.type` → `payload` 주요 항목 → Result 봉투 여덟 필드를 모두 적은 줄 → 상태 불변식 → (작업 트리에서 일하면 worktree) → tmp→mv → 멱등성 → History 금지. 그 뒤에 `protocols/` 참조 표.
   - `스킬` 절: 첫 문장은 `당신의 역할은 **"<유일한 질문>"**다.` 하나. 이어서 `task.skills`(워크플로 스킬의 절대 경로 배열)를 전부 읽는다는 것과, **워크플로 스킬의 각 절(`범위와 배치`, `규칙`, `판단이 갈리는 지점`, `확인 방법`)을 이 에이전트가 어떻게 쓰는지를 적은 표**를 둔다. 이 표는 사용자가 정한 내용을 정의 파일에 직접 적는 것이며 스킬로 빼지 않는다. 워크플로 스킬을 쓰지 않는 에이전트면 그렇게 적는다.
   - 수행 절차에서 프로젝트의 `CLAUDE.md`를 읽는다. 언어·도구에 관한 내용, payload 스키마의 반복, `protocols/`와 다른 규칙은 넣지 않는다. 사용자에게 묻지 않고, 다른 에이전트를 호출하지 않으며, `history.jsonl`·`context.json`·`job.json`을 쓰지 않는다.
2. **`protocols/task-result.md` 3.3 표**에 행(`request_type`, `status`, `blocked.type`)과 `request_type` 의미. 기존 `status` 값으로 표현되면 새 값을 만들지 않는다.
3. **`protocols/payload.md`**에 `### <name>` 절과 JSON 예시.
4. **`commands/orchestrate.md` §5.2**에 `**<name>**` 블록: 언제 보내는지, 돌아온 `status`마다 어디로 가는지. "현재 추가된 에이전트는 없다" 문장을 고친다. §5.1과 기본 세 에이전트의 값·라우팅은 바꾸지 않는다.
5. 받는 context가 기존 에이전트와 다르면 `protocols/context.md` 4.3과 orchestrate §3 표에 열.
6. `tests/check_docs.py`가 있으면(프레임워크 저장소) `AGENT_NAMES`·`STATUS`에 추가한다. §7로 확인한다.

### 3.1 `coder` 뒤에 붙는 에이전트

`coder`의 `DONE` 뒤에는 `reviewer` 말고도 에이전트가 몇 개든 붙을 수 있다(`protocols/task-result.md` 3.3.1). 이 경우 §2의 겹침 판정은 "`reviewer`의 읽기 검사와 관점 스킬로 표현되는가"로 본다. 표현되면 스킬로 풀고, 다른 도구·모델·절차가 필요하면 에이전트로 만든다. 만들 때는 §3에 더해 다음을 지킨다.

- `tools`에 `Edit`를 넣지 않는다. 산출물을 고치지 않아야 `reviewer`의 검증 호출과 병렬로 돌 수 있다. 테스트·빌드는 재실행하지 않는다(기본 검증의 몫).
- `status`는 `PASS`/`FAIL`/`BLOCKED`, `payload`에 공통 구조의 `findings[]`를 둔다. 새 값을 만들지 않는다.
- `description`에 검사 대상(어떤 파일·변경을 보는지)을 적는다. Orchestrator가 이번 변경에 해당 수정이 없으면 호출을 생략하는 근거다.
- orchestrate §5.2 블록의 호출 시점은 "`coder` `DONE` 뒤"다. 병렬 호출, 생략, 합산, `FAIL` 라우팅은 §5.0을 따르므로 블록에는 검사 대상과 `BLOCKED`의 행선지만 적는다.
- 같은 자리에 에이전트가 이미 붙어 있어도 더 붙일 수 있다. 검사 대상이 서로 겹치지 않는지만 본다.

## 4. 편입

1. 대상 파일을 읽고 진단 표를 만든다: `원본 절 | 내용 요약 | 처리(보존·교체·제거·이동) | 이유`. 도출한 유일한 질문을 표 위에 적고 §2로 겹침을 판정한다.
   - **보존**: 그 에이전트 고유의 판단 기준, 도메인 지식, 문체.
   - **교체**: 입출력 방식(채팅으로 받고 답하는 부분)은 Task 파일을 읽고 Result 파일을 쓰는 프로토콜로 바꾼다.
   - **제거**: 사용자에게 직접 묻기, 다른 에이전트 호출, 워크플로 상태 파일 쓰기, 특정 언어·도구의 명령(→ `CLAUDE.md`로 옮기자고 제안), 코딩 관례(→ `.claude/rules/`로 옮기자고 제안).
   - **이동**: 산출물 종류나 관점에 묶인 규칙은 정의 파일에 두지 않고 워크플로 스킬 후보로 뺀다(`skill-builder`).
2. 원본에서 알 수 없는 항목(호출 시점, 행선지, payload)을 §2의 설문으로 묻는다.
3. 진단 표와 §3의 결정 표를 함께 사용자 확인받는다. 버려지는 문장을 명시한다.
4. 원본은 지우지 않는다. §3의 1–6을 그대로 수행하되 정의 파일은 기존 절 구성으로 새로 쓰고 보존 항목을 옮긴다.
5. 보고에 보존·교체·제거·이동 표를 붙인다.

## 5. 확장

- 대상 정의 파일을 고친다. 절 순서와 `프로토콜 (요약)` 불릿 순서를 유지한다.
- 워크플로 스킬을 쓰는 방식을 바꾸는 것이면 `스킬` 절의 표만 고친다. 워크플로 스킬 파일은 건드리지 않는다. `coder`가 지키는 방식과 `reviewer`가 확인하는 방식이 어긋나지 않는지(예: `coder`는 `low` 규칙을 무시하는데 `reviewer`는 `FAIL`시키는 경우) 함께 본다.
- `request_type`·`status`·`blocked.type`·payload 키가 바뀌면 §3의 2–5에서 해당하는 곳을 같이 고친다. 기본 세 에이전트의 `status` 집합은 바꾸지 않는다.

## 6. 삭제

1. 기본 세 에이전트면 거절한다.
2. `.claude/workspace/*/*/job.json`에서 `status`가 `IN_PROGRESS`인 job의 `tasks/*.json` 중 `target`이 그 이름인 것이 있으면 미루거나 사용자 확인을 받는다.
3. §3의 1–6에서 더한 것을 전부 지운다. 그 이름이 `agents/`, `protocols/`, `commands/`에 남지 않았는지 `grep`으로 확인한다.

## 7. 확인하고 보고한다

프레임워크 저장소에서 실행 중이면 `python3 tests/check_docs.py`를 돌려 실패가 0이 될 때까지 고친다. 사람용 개요 문서의 에이전트 표가 어긋났다는 실패가 나오면 그 표도 같이 고친다. 프로젝트의 `.claude/`에서 실행 중이면(검사기가 없다) 다음을 직접 확인한다: 정의 파일의 `request_type`·`status`·`blocked.type` 값 = `task-result.md` 3.3 표의 행, `payload` 주요 항목 = `payload.md` `### <name>` 예시의 최상위 키, orchestrate §5.2에 `**<name>**` 블록, Result 봉투 여덟 필드 줄, 역할 문장 하나. 보고에는 모드와 대상 이름, 고친 파일·절 표(`파일 | 절 | 변경`), 확인 결과, 추정한 항목, 사용자가 이어서 할 일을 적는다. 정의 파일 전문은 붙이지 않는다.
