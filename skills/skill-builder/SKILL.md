# 워크플로 스킬 만들기

규격은 `protocols/skill-spec.md`다(워크플로 스킬의 형식, 제약, 템플릿, 고치는 범위, 확인 항목). 시작하기 전에 읽는다. 이 문서는 절차만 적는다.

워크플로 스킬(`skills/<name>/`)은 주제 지식이고 모든 에이전트가 같은 파일을 읽는다. 그것을 각 에이전트가 어떻게 쓰는지는 스킬이 아니라 에이전트 정의 파일(`agents/<name>.md`의 `스킬` 절)에 있다. 새 산출물 종류나 새 검증 관점을 더하는 일은 **워크플로 스킬 하나를 만드는 일**이다. 이 `skill-builder`나 `agent-builder`처럼 `## 적용 대상` 절이 없는 것은 일반 Claude Code 스킬이다.

이 스킬은 에이전트 정의, `protocols/`, `commands/orchestrate.md`를 고치지 않는다. 요구가 기본 에이전트의 역할(해석·계획, 산출물 작성, 검증)로 되지 않고 다른 도구·모델·절차가 필요하면 스킬로 풀 수 없는 것이다. 그때는 멈추고, 새 에이전트가 필요한 경우이며 `agent-builder` 스킬로 만든다고 사용자에게 알린다(기준은 `protocols/task-result.md` 3.3.1).

## 1. 무엇을 만들지 정한다

경로는 프로젝트의 `.claude/` 기준이다. 규격은 `.claude/protocols/skill-spec.md`, 워크플로 스킬은 기본 제공 스킬을 포함해 전부 `.claude/skills/`에 있다. **새 스킬은 프로젝트의 `.claude/skills/<name>/`에 쓴다.**

그다음 `.claude/skills/*/SKILL.md`에서 `적용 대상`을 전부 읽고 기존 워크플로 스킬과 겹치는지 본다.

| 요구 | 만드는 것 |
|---|---|
| 새 산출물 종류를 만들고 검증해야 한다 | 워크플로 스킬 하나. `검증 방식: 기본 검증` |
| 기존 산출물에 검증 관점을 더한다(보안, 접근성, 성능 등) | 워크플로 스킬 하나. `검증 방식: 관점 검증`. 실행형에게도 주어져 처음부터 지켜서 만들게 하고, 기본 검증형에는 기본 검증과 따로 관점 검증으로 호출된다 |
| 기존 워크플로 스킬의 적용 대상 안에 들어가는 규칙 | 새 스킬이 아니라 그 워크플로 스킬의 확장. 기본 제공 스킬도 `.claude/skills/`에 있으므로 직접 고친다 |
| 에이전트가 워크플로 스킬을 쓰는 방식을 바꾸고 싶다(예: 검증형이 `low` 위반도 재작업시키게) | 스킬로 만들지 않는다. 그 방식은 에이전트 정의 파일의 `스킬` 절에 있으며 `agent-builder`의 확장으로 고친다 |
| 특정 에이전트만 알아야 하는 주제 지식을 에이전트 디렉터리에 두고 싶다 | 만들지 않는다. 주제는 전부 워크플로 스킬이다. 에이전트마다 다른 것은 쓰는 방식이고 그것은 에이전트 정의 파일에 이미 있다 |
| 코딩 관례(네이밍, 스타일, 특정 언어·프레임워크에서 팀이 쓰는 패턴) | 스킬을 만들지 않는다. `.claude/rules/`에 적는다고 사용자에게 알리고(권장 이름 `coding-convention.md`), 원하면 문안을 제안한다 |
| 쓰는 언어·프레임워크, 테스트·빌드·린트 명령, 도구 사용법 | 스킬을 만들지 않는다. 프로젝트의 `CLAUDE.md`에 넣는다고 사용자에게 알리고, 원하면 문안을 제안한다 |

요청에서 알 수 없는 것만 묻는다(`AskUserQuestion`이 있으면 그것으로, 한 번에): 적용 대상(어떤 파일·디렉터리), 무엇을 규칙으로 볼지와 그 중요도, 판단이 갈리는 지점. 추정한 항목은 보고에 "추정"이라고 적는다.

## 2. 워크플로 스킬을 만든다

1. `protocols/skill-spec.md` §5의 템플릿으로 프로젝트의 `.claude/skills/<name>/SKILL.md`를 쓴다. `name`은 kebab-case이고 디렉터리 이름과 같다.
2. `적용 대상`은 파일 패턴이나 디렉터리로 구체적으로 적고, 적용하지 않는 경우와 `검증 방식`을 적는다. Orchestrator가 스킬을 고르고 관점 검증을 생략할지 정하는 근거다. frontmatter와 이 절이 앞 20줄 안에 들어가야 한다.
3. `규칙`의 항목마다 앞에 `[finding 유형·중요도]`를 붙인다. 유형은 `implementation`/`architecture`/`requirement`, 중요도는 `high`/`medium`/`low`다. 새 값을 만들지 않는다. `medium` 이상의 위반은 검증형의 `FAIL`이 된다는 점을 생각해 중요도를 정한다.
4. **에이전트에 중립으로 쓴다.** "~를 `risks`에 적는다", "finding으로 기록한다", "`deviations`에 남긴다"처럼 특정 에이전트의 동작을 적지 않는다. 규칙은 "~한다/~하지 않는다"로, 확인 방법은 "무엇을 읽어 확인한다"로 적는다. 각 에이전트가 그것으로 무엇을 하는지는 에이전트 정의 파일에 이미 있다.
5. 판단이 갈리는 문제는 규칙으로 만들지 말고 `판단이 갈리는 지점`에 적는다.
6. `관점 검증` 스킬의 `확인 방법`에는 테스트·빌드·서버 실행이 필요한 항목을 넣지 않는다.
7. 규칙과 예시는 어느 언어·프레임워크에서나 성립하는 말로 쓴다. 특정 스택의 파일 이름, 명령, API가 필요해지면 그 부분은 스킬에 넣지 말고 따로 빼서 사용자에게 알린다. 명령과 도구는 `CLAUDE.md`, 코딩 관례는 `.claude/rules/`에 둘 내용이다.

## 3. 고치거나 지운다

- 수정: 워크플로 스킬은 한 파일만 고치면 모든 에이전트에 함께 반영된다. `적용 대상`을 넓히면 다른 워크플로 스킬과 겹치지 않는지 다시 본다.
- 기본 제공 스킬(`code-structure`, `doc-writing`)도 같은 방법으로 직접 고친다. CCForge를 다시 복사하면 덮어써지므로 고친 뒤 커밋해 두라고 사용자에게 알린다.
- 삭제: 프로젝트의 `.claude/skills/<name>/`를 지운다. `.claude/workspace/*/*/job.json`에서 `status`가 `IN_PROGRESS`인 job의 `tasks/*.json` 중 `task.skills`에 그 경로가 있으면 미루거나 사용자 확인을 받는다. 적용 대상이 명세·문서인 워크플로 스킬이 하나도 남지 않게 되면 지우지 않는다(명세 단계가 막힌다).

## 4. 확인하고 보고한다

`.claude/protocols/skill-spec.md` §7의 확인 항목을 하나씩 확인한다. 보고에는 만든·고친 파일, 적용 대상과 검증 방식, 규칙 수와 중요도 분포, 추정한 항목, 기존 워크플로 스킬과의 경계를 적는다.
