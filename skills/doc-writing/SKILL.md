# 문서·명세 작성

워크플로 스킬이다. 누가 읽어도 같은 주제 지식만 적혀 있고, 이것을 어떻게 쓰는지는 읽는 에이전트의 정의 파일에 있다. 프로젝트에 명시된 것(스타일 가이드·용어집, `.claude/rules/`의 팀 규칙, 기존 문서 체계의 관례)이 아래 기본 규칙과 다르면 프로젝트의 것이 우선한다.

## 적용 대상

- 산출물: 문서, 명세 (명세 단계 `phase: spec`의 step은 항상 이 스킬을 쓴다)
- 변경 파일: `*.md`, `docs/`, API 명세 파일. 코드 step과 같은 step에 섞지 않는다.
- 검증 방식: 기본 검증

## 범위와 배치

- 요구사항은 "어느 파일을 고친다"가 아니라 **누가 무엇을 알아야 하는가**로 해석한다. 대상 독자와, 독자가 문서를 읽은 뒤 할 수 있어야 하는 일을 먼저 정한다.
- 먼저 기존 문서 체계를 본다. 목차·디렉터리 구조, 스타일 가이드, 용어 정의, 같은 주제를 이미 다루는 문서.
- 영향 범위는 파일이 아니라 **문서와 절** 단위로 표현한다. 고칠 절, 새로 만들 절, 이 변경으로 낡아지는 다른 문서의 절, 깨지는 상호 참조·링크.
- 어느 문서의 어느 절에, 어떤 독자를 향해, 무엇을 담는지를 정한다. 한 문서를 둘로 쪼개거나 합치는 작업이면 절 단위 이동 매핑을 먼저 정한다.
- 배치는 기존 문서 체계의 관례를 먼저 따른다. 관례가 없으면 "독자가 이 정보를 찾을 때 어디를 먼저 보는가"를 기준으로 하고, 불확실하면 **그 정보를 쓰는 기능의 문서 옆에 둔다**. 범용 문서로 올리지 않는다.
- 이 변경으로 낡아지는 다른 문서의 절은 같은 작업 안에서 함께 고친다.
- 완료 기준은 확인할 수 있는 형태로 적는다. 서술된 동작이 코드와 일치한다, 링크와 예시가 유효하다, 스타일 가이드를 따른다, 대상 독자가 특정 작업을 수행할 수 있다. 명세 단계의 명세는 코드 단계의 유일한 근거이므로 "구현에 필요한 인터페이스·데이터 형식·오류 처리·경계 조건이 빠짐없이 정의되어 있다"를 완료 기준에 넣는다.

## 규칙

규칙마다 앞에 `[finding 유형·중요도]`가 붙어 있다.

- [implementation·high] 문서가 설명하는 동작은 코드를 직접 읽어 확인한 사실만 적는다. 추측으로 동작을 적지 않는다.
- [requirement·high] 명세(`phase: spec`)에는 구현에 필요한 인터페이스, 데이터 형식, 오류 처리, 경계 조건을 빠짐없이 정의한다.
- [architecture·medium] 같은 정보를 두 곳에 두지 않는다. 기존 문서에 들어갈 내용을 새 문서로 만들지 않으며, 기존 문서와 모순되게 쓰지 않는다.
- [implementation·medium] 링크, 상호 참조, 코드 예시, 명령 예시는 실제로 유효해야 한다.
- [architecture·medium] 대상 독자에 맞는 깊이로 쓴다. 입문 문서에 내부 구현 세부를 넣지 않는다.
- [implementation·low] 프로젝트의 스타일 가이드와 용어 정의를 따른다.

## 판단이 갈리는 지점

규칙 위반이 아니라 판단이 갈리는 문제다. 누구도 임의로 결론내지 않고 선택지와 트레이드오프를 정리해 사용자에게 넘긴다.

- 문서의 범위와 깊이(독자에 따라 갈린다)
- 문서를 나눌지 합칠지

## 확인 방법

- 문서가 설명하는 코드를 직접 읽어 대조한다.
- 링크와 상호 참조는 대상 파일·절이 실제로 있는지 확인한다. 예시 명령은 실행해 본다(테스트·빌드를 실행하지 않는 호출에서는 읽어서만 확인한다).
- 실행할 테스트가 없는 문서 변경이면 링크·예시를 확인한 방법을 기록으로 남긴다.
- **이번 변경 범위 밖의 기존 문서**는 위반으로 보지 않는다. 이번 변경이 그 문제를 새로 늘렸을 때만 위반이다.
