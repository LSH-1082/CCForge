# 워크플로 스킬 규격

`/lead` 워크플로가 쓰는 스킬 파일의 형식이다. 스킬 파일과 `skills/skill-builder/SKILL.md`, `skills/agent-builder/SKILL.md`가 이 문서를 가리킨다. 에이전트는 분석형·실행형·검증형 세 유형이고, 산출물 종류와 검증 관점은 유형이 아니라 스킬로 더한다.

## 1. 워크플로 스킬과 에이전트

워크플로 스킬은 `skills/<name>/SKILL.md`에 둔다. 코드 구조, 문서 작성, 보안처럼 어떤 산출물이나 관점에 관한 주제 지식을 담고, 모든 에이전트가 같은 파일을 읽는다. 한 에이전트가 한 Task에서 여러 개를 받을 수 있다.

- 그 지식을 각 에이전트가 어떻게 쓰는지(계획에 반영한다 / 지켜서 만든다 / 위반을 찾는다)는 스킬로 두지 않는다. **에이전트 정의 파일(`agents/<name>.md`)의 `스킬` 절에 직접 적는다.** `skills/` 아래에 에이전트별 디렉터리를 두지 않는다.
- Lead는 Task의 `task.skills`에 그 Task에 적용할 워크플로 스킬을 절대 경로로 넣는다.
- 같은 주제 지식을 에이전트마다 따로 적지 않는다. 규칙은 워크플로 스킬 한 곳에만 있고, 실행형이 지키는 규칙과 검증형이 확인하는 규칙이 같은 문장이다.
- 워크플로 스킬은 에이전트에 중립으로 쓴다. "~를 `risks`에 적는다", "finding으로 기록한다"처럼 특정 에이전트의 동작을 적지 않는다. 그것은 에이전트 정의 파일의 몫이다.

```
<스킬 루트>/                        프로젝트의 .claude/skills/
├── <name>/SKILL.md                워크플로 스킬 (여럿). `## 적용 대상` 절이 있다
└── <그 밖의 이름>/SKILL.md         일반 Claude Code 스킬(`skill-builder`, `agent-builder`). 워크플로 스킬이 아니며 Lead가 고르지 않는다
```

스킬 루트는 프로젝트의 `.claude/skills/` 하나다. 기본 제공 스킬(`code-structure`, `doc-writing`)도 CCForge를 설치할 때 여기에 복사되며, 프로젝트가 추가하는 스킬도 같은 곳에 둔다. 기본 제공 스킬은 프로젝트에 맞게 직접 고쳐도 된다. 다만 CCForge를 다시 복사하면 덮어써지므로 고친 것은 저장소에 커밋해 둔다.

## 2. 워크플로 스킬의 형식

- **frontmatter**: `name`(kebab-case, 디렉터리 이름과 같음)과 `description`. `description`에는 어떤 산출물·변경에 적용하는지를 적는다.
- **절**: 아래 제목을 그대로 쓴다. 에이전트 정의 파일이 제목으로 절을 가리킨다.

| 절 | 필수 | 내용 |
|---|---|---|
| `## 적용 대상` | 필수 | 산출물 종류, 변경 파일의 범위(파일 패턴이나 디렉터리. 적용하지 않는 경우도), `검증 방식`. Lead가 스킬을 고르고 관점 스킬을 붙일지 정하는 근거다 |
| `## 범위와 배치` | 선택 | 요구를 어떤 단위로 해석하고, 영향 범위를 어떤 단위로 표현하며, 산출물을 어디에 두는지. 완료 기준을 어떤 형태로 적는지 |
| `## 규칙` | 필수 | 지켜야 하는 규칙 목록. 규칙마다 앞에 `[finding 유형·중요도]`를 붙인다. 예: `- [architecture·high] 의존성 방향을 지킨다.` |
| `## 판단이 갈리는 지점` | 선택 | 규칙 위반이 아니라 판단이 갈려서 누구도 임의로 결론내지 않아야 하는 문제 |
| `## 확인 방법` | 필수 | 규칙을 지켰는지 무엇을 읽어 확인하는지. 변경 범위 밖의 기존 상태는 위반으로 보지 않는다는 점 |

`적용 대상`의 `검증 방식`은 둘 중 하나다.

| 값 | 뜻 | 누구에게 가나 |
|---|---|---|
| `기본 검증` | 산출물 종류에 관한 주제 스킬. step마다 고르며 둘까지다 | 그 step의 실행형 Task와 기본 검증 Task, 분석형이 계획할 때 |
| `관점 검증` | 여러 산출물에 걸치는 관점(보안 검토, 접근성 검토 등). 변경 파일이 `적용 대상`에 해당하면 붙는다 | 실행형 Task에도 넣어 처음부터 지켜서 만들게 하고, 기본 검토 팀원이 같은 검토에서 그 스킬만 놓고 한 번 더 훑는다(검토 팀원을 따로 두지 않는다) |

## 3. 에이전트 정의 파일과의 관계

- 에이전트 정의 파일의 `스킬` 절에는 워크플로 스킬의 절(`범위와 배치`, `규칙`, `판단이 갈리는 지점`, `확인 방법`)마다 그 에이전트가 무엇을 하는지를 적은 표가 있다. 어느 워크플로 스킬에나 똑같이 적용되는 방식만 적고, 특정 주제의 지식은 적지 않는다.
- 새 에이전트를 만들거나 이미 있는 에이전트 정의 파일을 편입할 때 이 표를 함께 쓴다(`skills/agent-builder`).

## 4. 제약

- 워크플로 스킬은 전부 `skills/<name>/`에 둔다. `skills/` 아래에 중간 디렉터리나 에이전트별 디렉터리를 만들지 않는다.
- 워크플로 스킬의 frontmatter와 `## 적용 대상` 절은 파일의 앞 20줄 안에 둔다. Lead는 컨텍스트를 아끼려고 스킬 목록을 만들 때 앞 20줄만 읽는다(lead §0.1).
- 워크플로 스킬 하나는 산출물 종류 하나 또는 관점 하나만 다룬다. 다른 워크플로 스킬과 `적용 대상`이 겹치지 않는다.
- `관점 검증` 스킬의 `확인 방법`에는 테스트·빌드·서버 실행이 필요한 항목을 넣지 않는다. 관점 점검은 읽기 검사이고, 테스트·빌드는 기본 검토가 한 번만 돌린다.
- 프로젝트에 명시된 것(`.claude/rules/`의 코딩 관례와 팀 규칙, `CLAUDE.md`의 언어·도구)이 있으면 그것이 스킬의 기본 규칙보다 우선한다고 워크플로 스킬 첫머리에 적는다.
- **스킬에는 언어와 도구에 관한 내용을 넣지 않는다.** 쓰는 언어·프레임워크, 테스트·빌드·린트 명령, 패키지 관리자는 프로젝트의 `CLAUDE.md`에, 특정 언어·프레임워크에 묶인 코딩 관례는 `.claude/rules/`에 둔다. 스킬은 어느 스택에서나 성립하는 말로만 쓴다. 자리는 셋이다. 언어·도구·명령은 `CLAUDE.md`, 코딩 관례를 포함한 팀의 약속은 `.claude/rules/`, 산출물 종류와 검증 관점에 따른 규칙은 워크플로 스킬.
- finding 유형은 `implementation`/`architecture`/`requirement`, 중요도는 `high`/`medium`/`low`다. Lead의 라우팅이 이 값에 묶여 있으므로 새 값을 만들지 않는다. `medium` 이상의 위반은 검증형의 `FAIL`이 되고 `low`는 `PASS`와 공존한다.

## 5. 워크플로 스킬 템플릿

```markdown
---
name: <kebab-case>
description: <어떤 산출물·변경에 적용하는 워크플로 스킬인지>. 모든 에이전트가 같은 내용을 각자의 정의 파일이 정한 방식으로 쓴다.
---

# <이름>

워크플로 스킬이다. 누가 읽어도 같은 주제 지식만 적혀 있고, 이것을 어떻게 쓰는지는 읽는 에이전트의 정의 파일에 있다. 프로젝트에 명시된 것이 아래 기본 규칙과 다르면 프로젝트의 것이 우선한다.

## 적용 대상

- 산출물: <종류>
- 변경 파일: <패턴·디렉터리>. <적용하지 않는 경우>
- 검증 방식: <기본 검증 | 관점 검증>

## 범위와 배치

- …

## 규칙

- [<유형>·<중요도>] <규칙 문장>

## 판단이 갈리는 지점

- …

## 확인 방법

- …
```

## 6. 추가·수정·삭제 범위

| 하는 일 | 고치는 곳 |
|---|---|
| 새 산출물 종류나 새 검증 관점 추가 | 프로젝트의 `.claude/skills/<name>/SKILL.md` 하나. 에이전트별로 따로 쓸 것이 없다 |
| 기본 제공 워크플로 스킬 바꾸기 | `.claude/skills/<name>/SKILL.md`를 직접 고친다 |
| 워크플로 스킬 삭제 | 프로젝트의 `.claude/skills/<name>/`. 진행 중 job(`status: IN_PROGRESS`)의 `tasks/*.json`에 그 스킬 경로가 있으면 미루거나 사용자 확인을 받는다. 명세·문서가 적용 대상인 워크플로 스킬이 하나도 남지 않으면 명세 단계가 `missing_resource`가 되므로 지우지 않는다 |

`protocols/`, `commands/lead.md`, `agents/*.md`는 고치지 않는다. 고쳐야 한다면 스킬로 풀 수 없는 요구(다른 도구·모델·절차가 필요한 새 에이전트, 에이전트가 워크플로 스킬을 쓰는 방식의 변경)이며 이 규격의 범위 밖이다. 에이전트를 만들거나 편입하는 일은 `skills/agent-builder`가 한다.

## 7. 확인 항목

스킬을 만들거나 고친 뒤 성립해야 한다. `[자동]`은 기계적으로 확인할 수 있는 항목이다. 이 목록을 읽어 직접 확인한다.

- [자동] `skills/` 아래에 에이전트 이름의 디렉터리가 없다.
- [자동] `skills/<name>/SKILL.md`는 `name` = 디렉터리 이름이고 `description`, `## 적용 대상`(`검증 방식` 포함), `## 규칙`, `## 확인 방법`이 있다. frontmatter와 `적용 대상`이 앞 20줄 안에 있다.
- [자동] `규칙`의 항목마다 앞에 허용된 `[유형·중요도]`가 있다.
- [자동] 워크플로 스킬에 특정 에이전트의 동작(`risks`에 적는다, finding으로 기록한다, `deviations` 등)이나 특정 스택의 용어가 없다.
- [자동] 적용 대상이 명세·문서인 워크플로 스킬이 하나 이상 있다(명세 단계).
- [수동] 워크플로 스킬 하나가 산출물 종류 하나 또는 관점 하나만 다룬다. 다른 워크플로 스킬과 적용 대상이 겹치지 않는다.
